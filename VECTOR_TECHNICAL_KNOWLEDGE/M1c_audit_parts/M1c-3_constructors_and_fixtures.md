## Part 1 — Persistent-state constructor audit

| Class | Constructor signature | Default when called with zero args | Explicit override | Env var honored |
|---|---|---|---|---|
| `GoalSystem` (`core/brain/goal_system.py:175`) | `__init__(self)` | **REAL production goal store** (via `_load_or_seed()` → `_get_memory()` → `EpisodicMemory()` → shared singleton). Zero-arg construction ALWAYS attempts a real read, and can trigger a real write (`_merge_new_seeds()`→`_persist()`) before any caller has a chance to override anything. | **None.** No `db_path=`/similar kwarg exists at all. Only way to isolate: set `VECTOR_DB_PATH` before the FIRST `core.memory.episodic` import in the process, or bypass `__init__` via `GoalSystem.__new__(GoalSystem)` (the M1 fix pattern). | `VECTOR_DB_PATH` (indirectly, via the shared `EpisodicMemory` singleton) |
| `PolicyMemory` (`core/memory/policy.py:20`) | `__init__(self)` | Construction itself does nothing (just logs) — but **every single method** (`get_score`, `update_from_outcome`, `get_veto_count`, `record_suppression`, `get_stats`, etc.) independently calls `core.memory.episodic.get_temp_cursor()` against the SAME shared singleton connection. No isolation exists at construction time at all — the danger is per-method-call, not per-instance. | **None.** No `db_path=` kwarg exists. | `VECTOR_DB_PATH` (indirectly, via the shared `EpisodicMemory` singleton) |
| `EpisodicMemory` (`core/memory/episodic.py:735`) | `__init__(self)` | **REAL production DB**, unconditionally — calls the module-level `get_db_connection()` singleton with no override possible from the constructor. | **None** at the class level. Isolation is 100% external: set `os.environ["VECTOR_DB_PATH"]` before `get_db_connection()` is ever called anywhere in the process (first call wins and is cached in the `_db_connection` global for the rest of the process). | `VECTOR_DB_PATH`, read fresh at call time by `core/memory/db_utils.py::configured_db_path()` — BUT only on the very first call; a process-wide singleton (`_db_connection` global in `episodic.py`) caches the connection after that, so setting the env var AFTER any earlier `EpisodicMemory`/`get_db_connection()` call in the same process has NO effect. |
| `EpistemicTracker` (`core/brain/epistemic_tracker.py:29`) | `__init__(self, db_path=None)` | **REAL production `data/epistemic.db`** if `db_path` is omitted (`_DEFAULT_DB = CONFIG["data_dir"]/epistemic.db`). | **Yes** — explicit `db_path=` kwarg. | **`VECTOR_DB_PATH` is NOT honored at all.** A test that sets `VECTOR_DB_PATH` (believing it isolates "the database") does **NOT** isolate this store — it uses a completely separate, hardcoded default path with no env var hook whatsoever. This matches R12-H's prior finding, independently re-confirmed here by direct source read. |
| `CounterfactualMemory` (`core/memory/counterfactual.py:58`) | `__init__(self, db_path=None)` | **REAL production `data/counterfactual.db`** if omitted. | **Yes** — explicit `db_path=` kwarg. | **Not honored** — same gap as `EpistemicTracker`. |
| `PlanStore` (`core/runtime/plans.py:443`) / `get_plan_store()` (`:548`) | `PlanStore(path=None)`; `get_plan_store()` is a **module-level cached singleton** (`_PLAN_STORE` global) | **REAL production `data/plans/plans.json`** (JSON file, not SQLite) if `path` omitted; `get_plan_store()` always returns the same cached instance once constructed anywhere in the process — a later call cannot re-isolate it. | **Yes** on the class (`path=` kwarg) — but `get_plan_store()`, the function every real production caller (`goal_system.py::_decompose_to_plan`, `autonomous_loop.py::_get_plan_candidates`) actually uses, has **no** override mechanism at all. | None (not SQLite; no `VECTOR_DB_PATH` relevance). |

**Verdict on Part 1:** three distinct, INCONSISTENT isolation mechanisms coexist in this codebase:
(a) `GoalSystem`/`PolicyMemory`/`EpisodicMemory` — env-var-only, first-caller-wins singleton, no constructor override;
(b) `EpistemicTracker`/`CounterfactualMemory` — constructor-kwarg-only, env var silently ignored;
(c) `PlanStore` — constructor-kwarg on the class, but the actual production accessor (`get_plan_store()`) is an unoverridable singleton.
**A developer (or agent) who isolates via `VECTOR_DB_PATH` alone (the pattern this whole session has used) correctly isolates group (a) but leaves groups (b) and (c) silently touching real production files.** No test file was found that sets both an env var AND passes `db_path=`/`path=` to the group (b)/(c) classes it also happens to construct — this specific combined gap was not directly observed in the wild, but the constructor-level evidence proves it is possible.

## Part 2 — Test fixture isolation assessment

**`tests/conftest.py` (the ONLY conftest for the main ~5,000-test suite) — read in full.** Contains exactly one `autouse=True` fixture: `_reset_permission_gateway_singleton`, which resets `PermissionGateway._shared = None` before/after every test (for an unrelated reason — a 2026-07-21 singleton fix that broke dozens of tests expecting a fresh gateway instance). **There is no database isolation fixture of any kind** — no autouse temp-DB setup, no `VECTOR_DB_PATH` override, no monkeypatching of `get_db_connection`/`configured_db_path`. This independently confirms and strengthens R12-H's prior finding ("no global conftest.py fixture isolating the test suite from the real production DB") — verified here by reading the complete, current file content, not inferred. **Classification: (d) environment-variable-dependent, per-file, with ZERO global backstop — the weakest of the five classification options for the entire main suite.**

`VECTOR_TECHNICAL_KNOWLEDGE/learning_lab/tests/conftest.py` — session-scoped autouse cleanup of `vector_twin_*` temp directories (previously documented this session). This is a cleanup fixture, not an isolation fixture — isolation there is achieved by the Digital Twin Lab's own `IsolatedVectorEnv` class (`isolation.py`), which every lab test is expected to use explicitly. Not re-verified line-by-line in this pass (out of this fork's scope); flagged as a secondary, lower-priority area.

Other `conftest.py` files found (`vectorcode/python/tests/*`, `core/trading/tests/`, `districts/investment/vector_backtest/tests/`, `districts/intelligence/shadowbroker_server/**/tests/`) are scoped to unrelated subsystems, not inspected in depth here (out of scope for the goal/policy/episodic hazard this audit targets).

### Un-isolated test files beyond the 3 already fixed in M1

Cross-referencing every test file that constructs `GoalSystem()`/`PolicyMemory()`/`EpisodicMemory()` (26 files) against every file that mentions `VECTOR_DB_PATH` anywhere (29 files) surfaces **10 files that construct one of these classes for real, with no `VECTOR_DB_PATH` override anywhere in the file, and no mocking (`MagicMock`/`patch`/`monkeypatch`) as a substitute** (confirmed via a separate mock-usage grep — zero hits across all 10):

- `tests/test_e2_outcome_attribution.py`
- `tests/test_e3_learning_persistence.py`
- `tests/test_e4_update_rule.py` — **inspected in detail**: real `PolicyMemory()`, uuid-unique `action_type` keys per test (deliberate collision-avoidance, not isolation).
- `tests/test_task92_r7_decision_candidate_correlation.py`
- `tests/test_counterfactual_block_penalizes_policy.py`
- `tests/test_policy_reward_identity.py` — **inspected in detail**. Its own docstring explicitly, knowingly documents the lack of isolation ("PolicyMemory has no db_path override... uuid-unique action_types per test so nothing here can collide with real production rows") — a deliberate prior-task design choice (Task 89, Agent D), not an oversight. However this file goes further than pure key-uniqueness: it calls `core.memory.episodic._create_tables(get_db_connection())` directly against the **real production connection** to test schema-migration idempotency, and does a real raw-SQL fixture-row INSERT/read against the real `policy_memory` table. This is real, intentional production-DB access for a genuine "does the real migration harm real rows" test — a materially different risk profile from the other 9 (deliberate real-schema test vs. incidental real-store growth).
- `tests/test_crawl4ai_provider_and_persistence.py`
- `tests/test_episodic_sqlcipher_cross_contamination.py` — **inspected**: explicitly, by design, does "a real read against the real DB" to verify SQLCipher opens correctly; the file's own comment confirms this is intentional and (per the one line inspected) read-only, not a mutation risk. Not fully verified for a mutating call elsewhere in the file (out of this pass's depth).
- `tests/unit/test_memory_stores.py`
- `tests/test_point_system.py`

**Two of these ten were inspected in full detail** (`test_e4_update_rule.py`, `test_policy_reward_identity.py`) and confirmed to follow a **deliberate, documented "uuid-unique keys, no isolation" pattern** — real writes to the real `policy_memory` table under collision-proof random keys, growing the table with permanent test noise but not corrupting any meaningful existing row. **The remaining 8 files' exact risk profile (unique-key pattern vs. genuine oversight vs. read-only) is UNVERIFIED — classified UNKNOWN, not assumed safe, per the audit's own classification rules.**

### Two additional, previously-undocumented hazards found in production modules' own `__main__` self-tests (not test files — this is new for this audit, beyond what R12-H covered, which only looked at `tests/`)

- **`core/memory/policy.py:265-289`** (`if __name__ == "__main__":`) constructs a real, unisolated `PolicyMemory()` and calls `update_from_outcome()` three times under a `uuid`-suffixed key — same "unique key, no isolation" pattern as the test files above, confirmed by direct read. Real writes to the real `policy_memory` table on every direct run of this file.
- **`core/memory/episodic.py:1440-1455`** (`if __name__ == "__main__":`) constructs a real, unisolated `EpisodicMemory()` and: (a) `mem.store(...)` twice — real writes to `episodic_memory`; (b) `mem.remember('owner_name', 'Arghyadeep', 'identity', 1.0)` — a real write under a **fixed, non-random key** to `semantic_memory` (harmless in content today since it matches the real owner's actual name, but not isolated, and not namespaced against future accidental collisions); (c) **`mem.store_chain('exam tomorrow', ['study'], ['opened notes','read chapter'], 'set reminder', 'reminder set', 0.9)`** — a real write of **entirely fabricated, synthetic content into `reasoning_chains`**, one of the five tables `.claude/rules/memory.md` explicitly marks "Never Rename" and documents as becoming real LLM training data (RULE 8). This is the single most severe finding in this audit: a fabricated "exam reminder" scenario that never happened is indistinguishable from real reasoning history once written, with a direct documented path to training-data contamination.

Neither of these was executed to confirm — both are confirmed by direct, complete reading of the `__main__` block's source code, cross-referenced against the constructor findings in Part 1 (both classes are confirmed unisolated-by-default there).
