## Phase 5 — Orchestrator Synthesis (Section 5 of the mission, answered explicitly)

1. **What causal capability is already latent?** A real, structured, SQLite-persisted directed graph (`CausalGraph`) already receives a real write on every real dispatched action's real outcome, with real graph-traversal algorithms already implemented and unit-tested. The infrastructure to STORE a causal edge is not latent — it is built and running. What's latent/missing is (a) state-conditioning of the edge key, (b) honest confidence via observation accumulation, and (c) any reader on the real decision path.
2. **What exact causal link is missing?** The link from "VECTOR has already recorded that action A tends to produce outcome B under conditions like the present" to "this fact should nudge a live real decision between competing candidates." Today that link is fully absent — `DecisionEngine` never queries `CausalGraph`.
3. **What existing substrate should carry it?** `core/memory/causal_graph.py::CausalGraph`, extended (not replaced) to (a) key nodes/edges by `(action_type, state_key)` instead of `action_type` alone, using the SAME real, already-proven `context_snapshot["presence"]` field R22 established, and (b) accumulate `(hit_count, running_avg_strength)` per edge instead of overwriting on repeat, mirroring `PolicyMemory`'s own `sample_count>=3` honesty precedent for when a "confidence" claim is statistically meaningful.
4. **What is the smallest implementation?** (i) Add a `hit_count` column + accumulation logic to `CausalGraph.add_edge()`/its DB insert (a legitimate schema extension to an existing table, not a new table). (ii) Add a small, real, importable `causal_state_key(context_snapshot)` helper (single source of truth) used by BOTH the existing writer (`autonomous_loop.py:1383-1395`, modified to compute and include the state key in its node ids) and a new reader. (iii) Add `DecisionEngine._causal_factor()`, architecturally identical in shape to `_capability_factor()`/`_workload_factor()` (a lazy-init `_get_causal_graph()` getter, a bounded, small, symmetric multiplier, `reasoning_chain` entry), gated by a minimum real observation count before it ever deviates from neutral.
5. **BEFORE capability:** VECTOR's real, already-recorded action→outcome history (via `CausalGraph`) cannot influence any real decision — it is written on every action and never read by anything decision-relevant. Two candidates with identical formula inputs but wildly different REAL historical track records (one that has repeatedly, demonstrably succeeded under the current real state; one that has repeatedly, demonstrably failed) score and rank IDENTICALLY today.
6. **AFTER capability:** the same two candidates now score differently — the one with a real, accumulated, state-matching history of favorable outcomes receives a small real boost; the one with a real accumulated history of unfavorable outcomes receives a small real penalty; a candidate with no/insufficient real history remains neutral. The winner can genuinely change as a direct, traceable, attributable consequence of VECTOR's own real, self-accumulated experience.
7. **What experiment could falsify the claim?** Ablate (empty `CausalGraph`) → decision must return to the pre-R24 baseline winner. Swap the state (`presence=absent` vs `presence=present`) with the SAME accumulated history → decision must NOT be influenced by history that was accumulated under the other, unrelated state (scope control). Swap which action accumulated the favorable history → the favored candidate must swap accordingly, not stay fixed to a hardcoded name (intervention control).
8. **How does R24 remain distinct from PolicyMemory / CounterfactualMemory / R6 / R22 / R23?** `PolicyMemory` keys on `(action_type, situation_hash-of-full-params)` — far finer-grained, no state/context dimension, no graph structure, no traversal. `CounterfactualMemory` is pure text-similarity over REJECTED proposals only — never touches approved-and-executed outcomes. R6 (staleness-diversity) never looks at outcome quality at all, only repetition. R22's `_situational_factor()` reads raw current `presence`, with zero memory of past outcomes. R23's `_capability_factor()`/`_workload_factor()` read live registry/plan state, again with zero notion of accumulated historical outcome quality. R24 is the ONLY factor that answers "what has historically, causally, followed from doing this, under conditions like now" — a genuinely new axis, not a relabeling of any existing one. `context_snapshot["presence"]` is reused only as the antecedent-state KEY, not as R24's mechanism itself — R22's own semantics (boost absent+GREEN) are completely untouched.

Design explicitly scoped to L0-L4 on the mission's own classification (stored, retrieved, influences decisions, learned from real experience, changes later real behavior) — L5 (transfer to materially different situations) is deliberately NOT claimed: state-scoping is a Scope Control requirement (an edge learned under one state must not affect an unrelated state), so cross-situation transfer is an explicit non-goal for R24, not a gap — that generalization axis is R21's own, already-proven, separate capability.
